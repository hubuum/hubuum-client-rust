Compatibility evidence and history¶

The client and server are versioned independently. A client release "targets" a server release when its pinned OpenAPI contract comes from that server tag and the complete Docker-backed library and consumer integration suites pass against an immutable image for the same release.

Client 0.17.0 provides typed helpers for every route in the pinned v0.0.20 contract. Authenticated relative routes remain available through raw() as an extension point for additional operations.

Forward compatibility¶

Client 0.11.1 introduced the fresh credential approval API for servers incorporating PR 423. That release kept its declared v0.0.15 target, pinned image, and OpenAPI snapshot. Existing calls do not require the approval endpoints. On an enforcing server, credential mutations return reauthentication_required until the caller uses the explicit approval workflow.

Focused live verification on 2026-09-19 used the PR's merged source revision 3a1c44c938cc9d06d665229612c0fb1b4f3c98c8 and immutable Linux amd64 image ghcr.io/hubuum/hubuum-server@sha256:62438f2473ee15f9699ccc904e79c4c20c27e06a1219986c04493d269127f3e0. With HUBUUM_INTEGRATION_EXPECT_CREDENTIAL_APPROVALS=1, async and blocking token creation/renewal preserved approved expirations, and downstream user/password and credential-import dry runs passed. Blocking and async full restore confirmation and recovery passed with and without history. These focused checks supplement the required complete pinned-server run; they do not declare compatibility with all other changes on server main.

The canonical complete pinned-server command also passed on 2026-09-19 against the v0.0.15 image declared in Cargo.toml, including library and downstream consumer tests and all four restore/recovery scenarios. The new credential scenarios passed through the original APIs without requiring approval support.

After the fixture repairs in client PR 95, the complete library and downstream consumer integration suite passed on 2026-09-22 against immutable server candidate 61f1bfd3455af26254e1dc73e697a80b0536813a, image ghcr.io/hubuum/hubuum-server@sha256:8944a31e47ff97eb14bf5072772149c06d87714a316db54aa4e010195c5811a0. Approval enforcement was required, and all four full restore/recovery variants passed. This extends the earlier focused evidence to the complete suite. This evidence preceded publication of v0.0.16. Client 0.11.2 targets the released artifact and reviewed contract as described below.

Required CI is deterministic and stays pinned to the declared target. Scheduled jobs separately compare the contract and run the integration suites against the server's main branch. Those scheduled checks are early-warning signals; they do not change a published client's declared target.

Client 0.18.0 release¶

Client 0.18.0 adds typed related-object filter groups for class object lists by ID or name in both client modes. Existing 0.17.0 callers need no migration. The release retains server v0.0.20, its immutable image ghcr.io/hubuum/hubuum-server@sha256:eaf59f8a4b4793030a78bc1637a8e2b9fad2f810b8621ff9a874dca534b9a23a, the 257-operation snapshot, 125 wire-model mappings, Rust 1.88, and all public feature combinations.

On 2026-10-23, the canonical combined command passed with credential approval enforcement against that image:

HUBUUM_INTEGRATION_EXPECT_CREDENTIAL_APPROVALS=1 \
  ./scripts/run-integration-tests.sh --with-e2e-client -- --test-threads=1

The run passed 107 library tests, 56 ordinary consumer cases (including four historical server-version gates), three native-resource phases, and all four restore/recovery pairs. Related-filter authorization and grouping, live session rotation and persistence, LDAP/LDAPS, and restore recovery passed in both client modes. Local containers used a rootless Podman wrapper with --userns=keep-id:uid=0,gid=0 and disabled SELinux labels for fixture mounts; the pinned images and fixture contents were unchanged.

The complete workspace suite passed 958 non-container tests, including all 30 trybuild cases. Formatting, generated-code reconciliation, strict Clippy/rustdoc, all five public feature combinations, Rust 1.88 across every workspace target and feature, and pinned OpenAPI validation/comparison passed. All 202 applicable public API checks passed against v0.17.0 with additive compatibility required.

The tracing capture regression failed on the original harness when pagination callsites were first used on a thread without a scoped subscriber. Keeping a registry dispatcher alive avoids the upstream single-dispatch interest-cache bug without installing a global subscriber or changing client instrumentation. The regression passed with the fix, followed by 100 consecutive foundations runs with 16 test threads: 6,700 passing cases. This is an internal test-harness fix.

The dependency refresh updated smallvec from 1.16.3 to 1.16.4. All direct and compatible transitive dependencies are current; removing the Rust-version restriction found no additional updates. generic-array remains at 0.14.7 because upstream crypto-common 0.1.7 requires that exact version. Advisory, license, ban, and source checks passed. The audit used temporary Cargo and advisory caches to avoid home-filesystem lock failures.

Breaking Rust API: token accessors return owned, fallible snapshots. Use client.token()?.as_str() only for immediate access and sign in again after SessionExpired. Clones share rotating session state; refresh uncertainty invalidates that state rather than replaying the single-use credential.

Upgrade all API, worker, and restore binaries together during the server's offline migration, retain a pre-upgrade PostgreSQL snapshot, and sign in again. Backup format 10 preserves shared computed-definition history; the client recognizes formats 6–10 and preserves section contents.

v0.0.19 target¶

Client 0.15.1 retains this target and adds the versioned tracing contract. On 2026-10-19, the canonical combined integration command passed against the same immutable server image: 99 library tests, 38 ordinary consumer cases (including four historical version gates), three native-resource phases, and all four blocking/async restore-and-recovery pairs. The release also passed 774 workspace tests, every supported feature combination, Rust 1.88 across all workspace targets and features, Clippy, documentation, generated-code and OpenAPI checks, and dependency advisory/license/source checks. No endpoint or wire-model changes were introduced. Temporary Podman fixture mounts used SELinux relabeling on the local verification host; required CI continues to use the pinned Docker setup.

Client 0.15.0 targets the released server v0.0.19 image recorded above. Its 240-operation snapshot matches the authoritative tag. All five new query-usage operations have typed async and blocking helpers, as do the seven system notification operations previously available only through raw().

Observation settings, event-time authentication subjects, subject subscription filters, relation-inclusive audit queries, and backup format 9 are covered. Existing structured search remains available. Native index preparation and cleanup run through the separate server hubuum-admin --reconcile-query-usage command; the HTTP analysis route only reports evidence and suggestions.

Rust migration: exhaustive EventSubscriptionFilter literals must include subject_principal_ids, subject_identity_scopes, and subject_is_admin, or use ..Default::default(). Rust 1.88 and feature definitions are unchanged.

Server migration: follow the release's migration procedure and preserve a pre-upgrade backup for rollback. Collection integration APIs¶

Client 0.14.0 introduced these APIs as optional extensions after v0.0.17. Client 0.14.1 includes them in its declared released-server v0.0.18 contract. Older servers return their unsupported-route response; these methods do not fall back to global administrator discovery.

Use client.collection(id).event_sinks() to discover permitted destinations and create a webhook with NewEventSink.config containing destination_url. The same resource supports reads, edits, deletion, cursor pagination and conditional writes. Use client.event_subscriptions(id) to select events. Writes require both ManageEventSubscription and ReadAudit on the collection.

Administrators can use event_sink_collections, grant_event_sink and revoke_event_sink for global sinks. Collection-owned sinks cannot be shared. URLs in collection discovery are write-only, and credentials cannot be redirected by subscription routing. Provision a fixed destination for credential-bearing webhooks before using the newer server. Grants do not inherit to child collections.

Client 0.14.1 recognized backup formats 6, 7, and 8. Its CURRENT_BACKUP_VERSION was 8, matching its pinned v0.0.18 server. Server v0.0.17 emits format 7 and cannot restore format 8. The server validates restore support.
