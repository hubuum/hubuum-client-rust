Server compatibility¶

The client and server are versioned independently. A client release "targets" a server release when its pinned OpenAPI contract comes from that server tag and the complete Docker-backed library and consumer integration suites pass against an immutable image for the same release.

Dedicated typed helpers do not necessarily exist for every server operation. Authenticated relative routes remain available through raw() while typed coverage evolves.

Client 0.19.0 retains the 0.0.20 target and immutable image. The typed-ID migration is documented in the migration guide.

Before upgrading¶

Client 0.19.0 targets server v0.0.20. Use fresh credential approvals for protected mutations, and review known typed API gaps. The client accepts backup formats 6, 7, 8, 9, and 10; the server decides whether it can restore one. For older Rust releases, check the linked migration notes before upgrading: added fields can break exhaustive struct literals and patterns.

Server v0.0.18 requires an offline upgrade from v0.0.17 and emits backup format 8; older servers cannot restore that format. Follow the canonical server upgrade and recovery instructions and backup compatibility. Use the server guide for the actual version transition rather than copying migration commands from an older client release.

v0.0.20 authentication migration¶

Use login_session(credentials, client_id) and session_providers() on the supported server. Legacy login() is retained only for older servers; there is no automatic authentication downgrade. Handle client.token()? as a short-lived, owned snapshot. After refresh failure, sign in again instead of retrying an old refresh credential. PAT injection remains supported and independent of sessions.

Upgrade the server and restore executor together using the offline upgrade guide. Retain a pre-upgrade backup and matching binaries for rollback. See the typed API gaps before relying on newly introduced server fields or operations.
